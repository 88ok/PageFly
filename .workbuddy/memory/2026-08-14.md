# 2026-08-14

## 修复：分享链接 # 锚点在 iframe 内定位失败
- 问题：上传 HTML 含页内锚点（`#section`），分享链接 `/v/<id>#section` 的 hash 被顶层查看页解析，但锚点元素在 iframe(srcdoc) 文档里，顶层找不到 → 无法滚动定位。
- 根因：查看页把用户内容用 `<iframe srcdoc>` 渲染，顶层文档没有这些锚点节点。
- 修复点：`src/render.js` 的查看页 `<script>`：
  - `scrollFrameToHash(hash)`：iframe `load` 后按 `getElementById` / `getElementsByName` 定位元素并 `scrollIntoView`。
  - 顶层 `hashchange` → 转发进 iframe；iframe 内部 `hashchange` → 同步回顶层 URL（便于再次分享深链）。
- 验证：本地 `dev-server.mjs` 上传带锚点 HTML，确认脚本注入、内容到达 iframe、深链返回 200、内联脚本 `node --check` 通过。
- 注意：iframe sandbox 含 `allow-same-origin`，故父页可访问 `iframe.contentDocument`（同源）。md 模式标题无 id，深链到 md 标题暂不支持。
- v1 commit（`d10c353`）：只监听 hashchange，未拦截 iframe 内点击 → 用户反馈"两个标题"问题（原生行为与 scrollIntoView 冲突）。
- v2 commit（`189e250`）：完全重写——拦截点击+preventDefault+scrollTop(offsetTop)精确控制。但 offsetTop 相对最近定位父级，对"左目录+右正文"容器布局算出位置错→仍可能"两个标题"。
- v3 commit（`85aab81`，已 push）：scrollToHash 回归原生 scrollIntoView({block:'start'})（布局无关，兼容嵌套滚动容器/定位父级）；保留点击 preventDefault（消除原生行为与JS滚动冲突）。用户场景：首入深链OK，页面内二次点#锚点失效→已解决。
- v4 commit（`57b321e`，已 push）：**彻底重构**——锚点脚本注入 iframe 内部（ANCHOR_FIX_SCRIPT），父页仅 postMessage 转发 hash。关键认知：前面三版都在「父页操作 f.contentDocument」脆路上打补丁，sandbox/时序导致不稳定，实测失效。
- 验证方式升级：puppeteer-core + 系统 Chrome（/Applications/Google Chrome.app）真实浏览器测试，模拟"左目录+右正文"定位布局，深链#sec2/页内点#sec3/再点#sec1 三用例 secN.top=0 且 h1 滚出，ALL PASS。
- 教训：iframe srcdoc 的 # 锚点修复，可靠做法是"逻辑注入 iframe 内部 + 父页 postMessage 转发"，而非父页直接操作 contentDocument。
